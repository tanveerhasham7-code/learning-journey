# Lab 13 — Wireshark Packet Analysis

**Status: Completed (18 November 2026; learner-confirmed practice, no screenshots or terminal output supplied).**  
This guide describes a safe packet-capture exercise on your own isolated lab network. The assistant has not captured traffic from your VMs and does not claim any real packet findings.

## 1. Objective

Use Wireshark to capture and inspect:
- ICMP echo request/reply packets generated by your own ping test.
- DNS query/response packets generated by a name lookup.
- Ethernet, IP, transport and DNS fields where present.

You will learn to identify source/destination addresses, protocols, ports (when applicable), and request/response behavior.

## 2. Safety and privacy

- Capture only traffic on your own computer and isolated lab VMs.
- Do not capture other people's traffic or connect to networks without permission.
- Avoid logging into websites, entering passwords, or generating private traffic during this exercise.
- A packet capture can expose device addresses, hostnames, DNS lookups and other sensitive metadata.
- Save only a short, sanitized capture. Review it before uploading; screenshots or a written summary may be safer than sharing a raw PCAP.
- Do not upload captures containing credentials, personal browsing, private IP plans you do not want public, or unrelated traffic.

## 3. Prepare the lab

Use your Kali VM and, if available, your own Ubuntu VM on the same isolated Host-only/Internal network.

On Kali, identify interfaces and addresses:

```bash
ip -br addr
ip route
```

Record the interface connected to your lab network (for example, `eth0`) and the actual Ubuntu IP address. Do not assume example addresses from another lab match your setup.

Check that Wireshark is installed:

```bash
wireshark --version
```

If the command is not found, check the Kali package manager and install Wireshark only if needed. Follow the installation prompts carefully. Do not change global capture permissions or run unrelated system changes just to start this lab.

## 4. Start a capture

1. Open Wireshark from Kali's applications menu or run `wireshark`.
2. Select the interface that carries traffic to your Ubuntu lab VM.
3. Start capturing on that interface.
4. If you are unsure which interface is correct, generate one ping and look for packet activity on the candidate interface.
5. Keep the capture short and limited to this exercise.

Do not select a monitor-mode wireless interface or capture unrelated network traffic.

## 5. Capture ICMP ping traffic

While capture is running, open a Kali terminal and ping your own Ubuntu VM using its actual IP:

```bash
ping -c 4 <UBUNTU_IP>
```

Return to Wireshark and stop the capture after the four requests and replies have appeared (if replies are allowed by the target).

Use this display filter:

```
icmp
```

Inspect an echo request and its matching echo reply, if present. Expand the packet details and record:
- Ethernet II: source and destination MAC addresses (if visible on the local Ethernet segment).
- Internet Protocol Version 4: source and destination IP addresses.
- Internet Control Message Protocol: type/code and identifier/sequence number.
- Whether a corresponding reply was received.

Typical IPv4 ICMP types:
- Echo request: type 8.
- Echo reply: type 0.

If no reply appears, record the actual result. A firewall or network configuration may block ICMP; do not claim successful replies unless you observed them.

## 6. Capture DNS traffic

Start a fresh short capture, or continue only after clearing your previous capture if you can clearly distinguish the new packets.

In a Kali terminal, generate a DNS lookup:

```bash
getent hosts example.com
```

If that does not generate a visible DNS query because of local caching or resolver configuration, use:

```bash
nslookup example.com
```

Use a domain appropriate for a basic test and do not include private/internal names. Stop the capture after the lookup completes.

Try this display filter:

```
dns
```

Inspect the query and response, if present. Record:
- DNS transaction ID.
- Query name.
- Query type (for example, A or AAAA).
- Source and destination IP addresses.
- UDP/TCP source and destination ports, when visible.
- Whether a response was received and what answer/response code it contains.

Traditional DNS commonly uses UDP port 53; TCP port 53 can also be used. Encrypted DNS traffic (such as DoH or DoT) may not appear as readable DNS messages in this filter. A cached lookup may also produce no new DNS packet.

## 7. Useful display filters

| Filter | Purpose |
|---|---|
| `icmp` | Show ICMP packets |
| `dns` | Show decoded DNS packets |
| `ip.addr == <UBUNTU_IP>` | Show IPv4 packets involving the target |
| `eth.addr == <MAC_ADDRESS>` | Show Ethernet packets involving a MAC address |
| `udp.port == 53` | Show UDP DNS-port traffic |
| `tcp.port == 53` | Show TCP DNS-port traffic |

Replace placeholders with actual values. Display filters only change which captured packets are shown; they do not change the underlying traffic.

## 8. Analyze request and response behavior

For each protocol, compare the request with the response:
- Are the source and destination addresses reversed in the reply?
- Does the reply match the request identifier or transaction ID?
- How long does the response take, if Wireshark displays timing?
- Are there retries, unanswered requests or error responses?
- Does the capture show the expected protocol?

Do not assume every request must receive a response. Record what the capture actually shows and note possible explanations without guessing.

## 11. Troubleshooting

- **No packets appear:** confirm capture is running on the interface carrying the lab traffic.
- **Wrong interface:** compare `ip -br addr` and `ip route` with the VMware network adapter.
- **No ICMP reply:** check target IP and lab network; the target firewall may block ping.
- **No DNS packet:** resolver cache or local DNS configuration may prevent a visible query; try `nslookup example.com`.
- **DNS response absent:** record that fact and inspect resolver/network configuration; do not claim a response.
- **Permission error:** use Wireshark's supported capture setup and follow Kali's package guidance. Do not broadly change permissions on system devices.
